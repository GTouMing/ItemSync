# 0005. 文件级版本 + 内容寻址存储

- 状态：已接受
- 日期：2026-11-01

## 背景

需求包含“版本控制”。做 Git 式的提交历史意味着要维护 diff/patch/合并器，成本远超收益；做整盘快照则重复存储严重。

## 决策

1. **内容寻址 Blob 存储**：`blobs/<sha256 前两位>/<sha256>`，不可变、只写一次；相同内容天然去重。
2. 每次 Sync Run 成功后，为每个内容变化的同步项追加一条 `FileVersion`（itemId、blobHash、size、mtime、权限位、sourceNodeId、syncRunId、createdAt）。
3. 版本保留策略：**默认每项保留最近 10 个版本**（按数量淘汰，不设时间维度），可按同步根配置；仍被“当前版本”引用的 Blob 不删。
4. 提供按 FileVersion 回滚单个文件；回滚作为一次新的本地变更参与后续同步，不篡改历史。
5. 版本历史是**节点本地**的，不跨节点自动复制。跨节点取历史属于后续能力。

## 后果

- 需要元数据存储：同步项索引、FileVersion、Tombstone、冲突、同步对、触发器。选型未定（SQLite via JDBC / H2 / 自研索引文件），需单独 ADR。
- 需要 GC 任务：先删 FileVersion，再删无引用的 Blob，必须与正在执行的 Sync Run 做引用互斥。
- 写入 Blob 必须“临时文件 + 原子 rename”，否则断电会产生半截内容。
- Android 上 Blob 存储占用受 SAF/应用私有目录限制，需要容量阈值与“仅 WiFi 时同步”类策略。

## 备选方案

- **整盘快照**：可整体回滚，但重复存储与时长大。
- **类 Git 提交历史**：能力最强，工期翻倍，二进制文件仍然无解。
- **只留上一版**：实现最简，称不上版本控制。
