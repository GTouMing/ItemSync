# 0031. 配对状态端点：独立元数据通道

- 状态：已接受
- 日期：2026-11-02
- 修订：[ADR-0033](0033-trust-without-short-code.md) 替代短码配对部分。
- 补充：[ADR-0030](0030-pairwise-trust-and-presence.md) 的配对流程与在线状态

## 背景

ADR-0030 要求同组设备互相可见并显示信任状态，但当前同步端口使用固定证书的 mTLS：未信任设备无法完成握手，因此也无法通过同步连接查询“对方是否信任我”。桌面端只能把连接成功当作双方已信任的推断，撤销后也不能立即反映远端状态。

需要在不削弱同步端口固定证书模型的前提下，提供一个权威的远端信任状态来源。

## 决策

1. 新增独立的配对状态端点，与同步端口分离；同步端口继续只接受 `TrustStore` 中已固定的证书指纹。
2. 配对端点绑定临时端口（`0`），实际端口通过 mDNS TXT 的 `pairingPort` 发布；`0` 表示对端不支持该端点。同步端口仍固定 `47800`。
3. 配对端点接受任意客户端证书，因为它的职责是读取请求方证书指纹；它只处理 `PAIRING_STATUS` 请求，返回本机 `nodeId`、`deviceId`、证书指纹和“是否信任请求方”。它不处理清单、Blob 或任何同步帧，也不修改信任状态。
4. 请求方固定 mDNS 公布的服务器指纹，并校验响应中的组 ID、节点/设备 ID 和证书指纹与发现结果及 TLS 会话实际指纹一致；任一不一致按 `UNKNOWN` 处理。
5. 6 位短码仍由组 ID 和双方真实证书指纹派生。只有状态查询成功且身份校验通过后才显示短码并允许本地确认信任；双方各自在本地确认，端点不做远程改信任。
6. 远端状态分为 `TRUSTED`、`UNTRUSTED`、`UNKNOWN`；成功结果缓存 30 秒，失败缓存 5 秒，设备列表打开或刷新时强制重新查询。
7. 只有桌面端启动配对端点；CLI、Android 和旧版本不发布 `pairingPort`，桌面端对它们显示 `UNKNOWN`。

## 后果

- 设备列表能区分“对方已信任你，等待本机确认”“已信任，等待对方确认”“已信任（双方）”，不再只靠连接结果推断。
- 同步端口的安全模型不变；配对端点接受任意证书的范围被限制在独立的、只返回元数据的 handler。
- 配对需要双方都支持配对端点；旧版本仍可同步已固定证书的设备，但无法显示远端信任状态或建立新配对。
- 临时端口可能被本机防火墙拦截，表现为 `UNKNOWN`；同步和显式本地信任不受影响。
- 知道组 ID 的局域网设备可以查询某个指纹是否被信任；这与 ADR-0029/0030 已接受的在线可见性一致，且不会泄露文件数据。

## 安全分析

- **主动中间人**：攻击者无法在不持有私钥的情况下通过固定指纹的 TLS 校验；若终止 TLS 再转发，双方短码分别基于攻击者指纹，无法同时与真实设备匹配。
- **伪造 mDNS**：客户端会固定到伪造指纹对应的证书，但短码与真实设备不一致，用户核对时能发现；响应身份字段也必须与发现结果一致。
- **重放**：查询只读，不改变信任状态；每次查询使用新的 TLS 连接。
- **文件数据**：配对端点没有 `MANIFEST_REQUEST`、`BLOB_GET` 处理路径，收到其他帧即关闭连接。
- **拒绝服务**：配对端点沿用现有 TLS 服务端的连接管理；单次查询有 2 秒超时，发送响应后关闭连接。

## 备选方案

- **在同步端口内查询**：未信任设备无法通过固定证书握手，无法覆盖目标场景，否决。
- **mDNS TXT 广播信任状态**：实现简单，但未认证、可伪造且状态过期，只能作为提示而不是权威状态，否决。
- **临时配对模式**：只在用户点配对时开端口，攻击面更小，但设备列表无法常驻显示远端状态，双方操作窗口也难对齐，暂不采用。
- **双向配对握手**：远程发起、对方弹窗批准，交互更顺，但引入状态机、超时、重放和并发处理；第一期先做只读状态查询。
