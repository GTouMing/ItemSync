# 0003. 闹钟触发器与条件触发器分开实现

- 状态：已接受
- 日期：2026-11-01

## 背景

需求同时提到“定时同步”和“计划同步”。用户已澄清二者语义不同：
- **定时同步** = 闹钟式：设定哪周、哪天的哪时哪分触发。
- **计划同步** = 条件式：由条件触发，例如目录内容更新、目标应用启动前后。

它们不是同一个调度器的两种参数，而是两类事件源。

## 决策

同步由 `Trigger` 抽象驱动，第一期两个实现：

1. `AlarmTrigger`（定时同步）
   - 规则：周几集合 + 时:分 + 时区 + 启用开关。
   - Windows：进程内调度器 + 系统时间/时区变更监听，睡眠唤醒后补跑错过的最近一次。
   - Android：`AlarmManager.setExactAndAllowWhileIdle`，需 `SCHEDULE_EXACT_ALARM` / `USE_EXACT_ALARM`；重启后由 `BOOT_COMPLETED` 重新注册。
2. `ConditionTrigger`（计划同步）
   - 条件源可组合：`DirectoryChanged`（目录变动）、`AppStarted` / `AppStopped`（仅 Windows，见 ADR-0008）。
   - 命中后进入**防抖窗口**（默认 30s，可配），静默期内新事件重置计时，窗口结束才发起 Sync Run。
3. 两者产出同一种 `SyncRunRequest`，交给同一个同步引擎；引擎不关心触发来源。
4. 手动“立即同步”是第三种触发器，绕过防抖但受“同一同步对不允许并行运行”约束。

## 后果

- 需要防抖/去重与“同一同步对串行化”的并发控制。
- 条件触发器在节点未运行时无法生效：Android 上依赖前台服务存活或 WorkManager 兜底；Windows 上依赖托盘进程存活。
- 闹钟在设备深度睡眠时可能延迟，UI 不得承诺“精确到秒”。

## 备选方案

- **统一成 cron 表达式**：用户明确这是两个不同的东西，强行合并会导致“条件”无处安放。
- **只做闹钟**：丢掉“目录变动自动同步”这一核心价值。
- **固定间隔轮询**：与用户定义的“定时”不符，且浪费电。
