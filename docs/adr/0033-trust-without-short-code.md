# 0033. 信任开关使用证书固定，不使用短码配对

- 状态：已接受
- 日期：2026-11-03
- 替代：[ADR-0030](0030-pairwise-trust-and-presence.md) 的短码配对部分；修订 [ADR-0031](0031-pairing-status-endpoint.md) 的短码说明。

## 背景

产品决定不需要 6 位短码配对。信任开关应该只是一个布尔开关：开启时固定当前发现/确认到的证书指纹，之后每次同步 TLS 握手校验对端证书是否与缓存一致。

## 决策

1. 信任开关按 `(组 ID, 对端证书指纹)` 保存布尔值，不再生成或核对短码。
2. 开启信任时固定当前设备发现与配对状态查询确认的证书指纹；首次信任是 TOFU，UI 必须明确提示不能防首次中间人。
3. 不新增“开启时发送证书”的应用层协议；TLS 握手本身交换并验证证书，信任层只保存指纹。
4. 出站同步握手发现证书与固定指纹不匹配时，立即撤销该对端的本地信任并产生 UI/通知警告。
5. 入站握手证书不匹配时拒绝连接并记录警告；服务端不自动猜测应该撤销哪条信任记录。
6. 证书变更后的恢复方式是用户手动“撤销信任 → 重新开启信任”，重新固定新证书。
7. 同步端口继续只接受固定证书；配对状态端点仍只返回身份和信任布尔值。

## 后果

- 首次信任无法抵御同一局域网内的主动中间人；这是去掉短码后的明确安全降级。
- 本地信任被撤销后，对方可能仍显示“已信任”；双方需要重新开启信任并重新固定证书。
- 入站证书不匹配只能告警，不能自动定位到某个 peer；出站路径可以准确撤销。
- 不再需要 `PairingCode`、短码确认弹窗和相关测试。

## 备选方案

- **保留 6 位短码**：能抵抗首次中间人，但产品认为没有必要，否决。
- **开启信任时交换完整证书**：仍无法证明首次证书归属，且增加协议面；TLS 握手已提供证书，否决。
- **证书不匹配只警告不撤销**：会继续保留一个已知不再匹配的信任记录，否决。
