# 0016. 交付顺序：共享核心 + CLI → Windows UI → Android

- 状态：已接受
- 日期：2026-11-01

## 背景

同步软件最贵的风险不是界面，而是“双向同步在冲突、删除、断电、重传下是否正确”。如果先做 UI，会在最不确定的部分之上堆一层确定的部分。

## 决策

1. **M0 引擎 + CLI**：共享核心（协议、Blob 存储、元数据、同步引擎、触发器）+ 命令行工具 `itemsync-cli`：
   - `pair`（生成配对码/二维码内容、导入对端指纹）
   - `sync`（手动触发一次同步）
   - `status`（同步对状态、最近运行、冲突数）
   - `log`（结构化日志导出）
   - `verify`（对比两棵目录树的内容哈希，用于验收）
2. 验收方式：同一台机器跑两个进程、两个数据目录，用真实同步场景（新增、修改、删除、冲突、断电恢复、大文件续传）验证。
3. **M1 Windows UI**：JavaFX 托盘应用 + 向导 + 冲突裁决 + 版本历史。
4. **M2 Android**：前台服务 + 通知 + 权限引导 + 最小 UI。
5. CLI 长期保留，作为运维与故障排查入口，不作为临时脚手架。

## 后果

- 早期没有图形界面，演示效果差，但正确性风险被前置。
- CLI 与 UI 必须共用同一用例层，禁止 CLI 走旁路逻辑，否则测试覆盖的就不是 UI 的路径。
- 需要一套“双进程测试夹具”（临时目录、随机端口、模拟时钟）作为引擎测试基础设施。

## 备选方案

- **Windows 闭环优先**：用户更早看见成品，但最容易在 UI 上返工。
- **Win↔Android 最小链路**：演示效果好，但 Android 权限与保活会把进度拖住。
- **两端并行纵切**：进度均匀，每步都付双重成本。
