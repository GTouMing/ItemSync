# 0004. 双向对等同步，冲突保留副本

- 状态：已接受
- 日期：2026-11-01
- 修订：**并发判定**由“base hash”改为“项级版本向量”，**传播模型**由两两配对改为同步组，见 [ADR-0021](0021-sync-group-version-vectors.md)。“双向 + 冲突副本”的核心策略不变。

## 背景

“一套代码完成发送端和接收端”意味着节点之间是对等的。若把设备分成发送端/接收端两种角色，就退化成主从备份，无法满足双向同步。

## 决策

1. 每个同步对是对称的：双方各自扫描同步根、交换 Manifest、计算差异、双向推拉。代码里**不存在** sender / receiver 角色，只有 `SyncPair` 的两个端点。
2. 方向语义由同步对的 `DirectionMode` 表达：`BIDIRECTIONAL`（默认）、`MIRROR`、`RECEIVE_ONLY`。
3. 冲突判定：为每个同步项维护“最后共同版本内容哈希”（base hash）。若双方各自相对 base 都发生了修改（含**删除 vs 修改**），判定为冲突。
4. 冲突处理：**绝不静默覆盖**。本地一方保留原名，对端内容写成冲突副本 `原名 (conflict <deviceId> <timestamp>).ext`；冲突记录写入冲突表，UI 汇总展示，用户可逐条裁决。
5. 删除通过墓碑传播：删除先记 Tombstone 再移除文件，避免“对端没有这个文件”被误判为删除。

## 后果

- 必须持久化每项的 base hash，否则无法区分“并发修改”与“单方修改”。
- 冲突副本会占用空间且不会被 GC 自动清理，需要 UI 引导清理。
- 目录级冲突（一方删目录、一方在目录内新增文件）规则需在实现时明确为“保留目录并保留新增文件，删除推迟”。

## 备选方案

- **主从镜像**：简单可预测，但不满足双向需求。
- **双向 + 三方合并**：文本可自动合并，但要维护 base 快照与合并器，且二进制无解；可作为后续的冲突策略插件。
- **单向互推伪装双向**：实现最省事，冲突全部甩给用户。
