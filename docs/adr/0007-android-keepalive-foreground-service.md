# 0007. Android 前台服务保活，失败靠闹钟恢复

- 状态：已接受
- 日期：2026-11-01

## 背景

Android 的后台限制是硬约束：Doze、应用待机分桶、厂商 ROM 的额外清理。用户要求“手机后台保活”，但任何方案都无法保证 100% 存活。

## 决策

1. **常驻前台服务**（`foregroundServiceType="dataSync"`）承载节点：网络监听、目录监听、同步引擎。
2. 权限与引导：
   - `POST_NOTIFICATIONS`（Android 13+），用于展示常驻通知。
   - `SCHEDULE_EXACT_ALARM` / `USE_EXACT_ALARM`，用于闹钟触发器。
   - `RECEIVE_BOOT_COMPLETED`，开机后恢复服务与闹钟。
   - 引导用户加入**电池优化白名单**（`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`），并在隐私政策中说明用途。
   - 对已知激进厂商（小米、华为、OPPO、vivo 等）提供“自启动/后台运行”设置页的跳转引导。
3. **被杀后的恢复**：AlarmManager 周期心跳唤醒并尝试重启前台服务；WorkManager 周期任务作为兜底。
4. UI 必须明示：保活是尽力而为，Doze 深度休眠期间可能延迟。

## 后果

- 常驻通知无法隐藏，需在首次运行时解释原因，否则用户会当成流氓软件。
- 应用商店审核需说明前台服务与精确闹钟的用途；`USE_EXACT_ALARM` 在部分商店/系统版本受限。
- 耗电投诉需要配套策略：仅 WiFi、电量阈值、夜间暂停。
- 前台服务被杀后由闹钟恢复存在窗口期，同步任务需要幂等与可续传。

## 备选方案

- **纯 WorkManager**：合规省电，但最小周期 15 分钟且 Doze 下不可靠，无法满足“文件变动即同步”。
- **不保活**：只在 App 前台可靠，与需求不符。
- **无障碍服务/UsageStats 强保活**：商店高风险，明确拒绝。
