# 0024. 开放入组（8 位组 ID）+ 双向同意的共享门禁

- 状态：被替代（ADR-0029 组 ID 命名空间、ADR-0030 信任模型）
- 日期：2026-11-01

## 背景

需求方选择：组 ID 8 位随机，**不存在入组审批流程**；新设备入组后，组内成员各自决定是否向它同步，以此“变相批准”。同时要求成员之间只能看到设备名、在线状态与同意关系，看不到目录名与文件名。

这意味着组 ID 是唯一的入组凭据，必须当成敏感信息对待。

## 决策

1. **入组**：持有组 ID 且可达的节点可直接加入成员表，无人工审批。
2. **可见性**：成员可见对端的设备名、平台、在线状态、与自己的同意关系；**不可见**同步根路径、目录名、文件名、版本与文件大小。
3. **共享同意**：成员两两独立设置；**只有双方都同意才建立同步**；单方同意不传输任何数据（避免“传了一半”的中间态）。
4. **必须配套的缓解措施**（不做就不算实现完成）：
   - 组 ID 为 **8 位，字符集 `[0-9a-z]`**（36 个字符，约 41.4 bit 熵），输入时大小写归一为小写。
   - 入组尝试**限流**：每节点每分钟最多 5 次，失败指数退避；被拒后静默丢弃，不回显“ID 是否存在”。
   - **组 ID 轮换**：任一组内成员可轮换，轮换后所有成员必须重新输入（成员表保留，但旧 ID 立即失效）。
   - **黑名单**：任一成员可将某设备从自己的视野中移除（不再接受其 NOTIFY，也不向其传播）。
   - 首次创建组的 UI 必须提示：组 ID 泄露 = 别人能看到你的设备名与在线状态。
5. 若用户要求更高强度，设置中可切换为 16 位组 ID（约 80 bit）。

## 后果

- 组 ID 泄露的损害是**元数据与存在性**泄露，而非文件泄露；文件仍需对方同意才能流动。
- 8 位 ID 在有人恶意枚举时靠限流兜底，不是密码学强度，文档不得宣称“安全”。
- 字符集含易混对（`0/o`、`1/l`），UI 必须用等宽字体展示并提供一键复制，避免用户抄错。
- 组 ID 轮换是重操作，需要全员重新输入，UI 必须给出预览与确认。
- 成员表本身是攻击面：伪造设备名需要长度与字符集限制。

## 备选方案

- **成员批准**：安全更好，被需求方否决（不想多一步审批）。
- **组 ID 即组密钥**：把 8 位 ID 直接当加密密钥，强度严重不足。
- **一次性邀请码**：体验接近，但增加一个一次性状态机。
- **签名邀请**：最安全，工程量最大。
