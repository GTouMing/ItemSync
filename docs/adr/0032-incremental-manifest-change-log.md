# 0032. 增量 manifest 使用变更序号与拉取/推送游标

- 状态：已接受
- 日期：2026-11-02
- 修订：[ADR-0035](0035-multi-group-single-root.md) `item_change`/`sync_cursor` 使用 `group_id`，manifest 帧不再使用 `rootId`。
- 补充：[ADR-0021](0021-sync-group-version-vectors.md) 的清单传输部分

## 背景

当前同步每次都发送完整清单，10 万项规模下开销与变更量无关。`MANIFEST_REQUEST` 已经带有 `since` 版本向量，但按项向量过滤不可靠：某路径的向量可能被其它项的更高 counter 覆盖，从而把客户端从未收到过的项误判为已拥有。

## 决策

1. 新增 `item_change` 表：每个 `(root, logical_path)` 只保留一行，`seq` 单调递增；每次 `Item` upsert 用新的 `seq` 覆盖旧行。迁移时回填现有 `item`。
2. `MANIFEST_REQUEST` 增加 `sinceSequence`，`MANIFEST_END` 增加 `sequence`；旧节点缺失字段按 `0` 处理，自动退回全量，不破坏现有同步。
3. 客户端按 `(root, peer)` 持久化拉取游标；只有 apply 成功后才推进。服务端返回的 sequence 小于游标时视为服务端数据库重建，回退一次全量。
4. 增量响应只包含远端变更项，规划器使用 `planPartial`：远端未返回的本地路径**不**视为远端缺失。
5. 本地变更推送使用每个 peer 的推送游标：本地变更序号大于推送游标时才发送 NOTIFY，发送成功后推进。
6. 服务端先生成带 sequence 的清单缓存，再按客户端序号过滤；缓存更新使用独立读写锁，不占用同步锁，避免两端同时同步时互相等待。
7. 快照必须“先读当前 sequence、再取 `<= sequence` 的变更”，防止把查询之后的新变更包含进来后客户端跳过。

## 后果

- 首次同步仍传全量；之后只传变更项，墓碑也按同一序号机制传播。
- `item_change` 只表达“当前路径的最新变更”，不保留历史；需要变更历史时必须另建日志表。
- 游标必须和本地元数据一起备份/清除；清空游标只会导致一次全量，不会丢数据。
- 服务端内存缓存按路径保存最新条目与序号；缓存一致性由独立读写锁保护，避免占用同步锁。

## 备选方案

- **仅按版本向量过滤**：实现最简，但会漏项，否决。
- **客户端上传完整清单摘要/Merkle**：无需数据库迁移，但协议轮次、分页对齐和内存开销更复杂，暂缓。
- **只做客户端 apply 优化**：网络仍传全量，不解决主问题，否决。
