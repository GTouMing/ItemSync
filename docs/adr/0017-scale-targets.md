# 0017. 规模指标：10 万项 / 单文件 10 GB

- 状态：已接受
- 日期：2026-11-01

## 背景

没有量化指标就无法判断“清单能否一次性载入内存”“哈希要不要并行”“比对要不要分页”。家用与小团队场景与百万级仓库是两个完全不同的架构。

## 决策

目标量级（单节点）：

| 指标 | 上限 |
| --- | --- |
| 每个同步根条目数（文件 + 目录） | 100,000 |
| 单文件大小 | 10 GB |
| 每节点同步组/同步根数量 | 5 |
| 信任邻居数量 | 10 |
| 单节点 Blob 存储 | 不设硬上限，提供容量预警 |

由此产生的要求：

1. 扫描**流式**：逐目录遍历，按批（默认 5,000 项）写入并在批间做差异比对，不把整棵树的 Manifest 放进内存。
2. 索引查询**分页**，禁止 `findAll` 式 API。
3. 哈希使用固定大小缓冲（1 MiB），按 CPU 核数受控并发，避免 IO 抖动。
4. 传输并发块窗口受内存上限约束，默认最多 8 块在途。
5. 引擎内存上限按 256 MB 堆做基准测试，作为 CI 约束。

## 后果

- 超过 10 万项的同步根允许添加，但 UI 必须提示“超出官方支持范围，行为可能变慢”。
- 需要一套大数据量测试夹具（生成 10 万个小文件、一个 10 GB 稀疏文件）。
- 分页 API 会让共享层代码比“内存一把梭”啰嗦，这是有意的。

## 备选方案

- **1 万项 / 2 GB**：实现最简，但一个照片库或代码仓库就能撑爆。
- **百万项级**：需要分片索引、增量扫描、持久化工作队列，工程量显著上升，第一期不做。
- **不设指标**：无法验证，架构会在第一个真实大目录上被推翻。
