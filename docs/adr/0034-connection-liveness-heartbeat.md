# 0034. 同步连接使用 PING/PONG 空闲检测

- 状态：已接受
- 日期：2026-11-03
- 关联：修订 [ADR-0031](0031-pairing-status-endpoint.md) 的连接生命周期；补充 [ADR-0033](0033-trust-without-short-code.md) §7 的已连接判定。

## 背景

同步连接是长连接。对端静默消失（进程被杀、Wi-Fi 断开、休眠）时不会发送 FIN；`FrameConnection` 的读线程会一直阻塞，`TlsRemotePeer.isConnected()` 和入站连接状态都不会翻转，设备列表因此继续显示“已连接”。

ADR-0033 §7 依赖连接状态判断双方信任，前提是这个“已建立”必须能及时变成“已断开”。TCP keepalive 的系统默认间隔通常以小时计，不能满足这个前提。

## 决策

1. 同步端口（47800）的 TLS 连接启用空闲检测：读超时 10 秒；超时后发送 `PING`；连续 2 个周期没有 `PONG`（约 30 秒）关闭连接。
2. `PING`/`PONG` 在传输层 `HeartbeatHandler` 处理，不透传给业务 handler。收到 `PING` 自动回 `PONG`；收到 `PONG` 只重置空闲计数。
3. 配对端点不使用心跳。它只处理单次请求/响应，使用 5 秒读超时，并在响应写出后关闭连接。
4. 心跳关闭连接后由 `PeerTrustCoordinator` 在下一轮 presence 扫描/重连中重建；心跳不修改信任记录，也不猜测远端信任状态。
5. 入站和出站同步连接都适用：出站由客户端发心跳，入站由服务端发心跳，两端各自能发现半开连接。

## 后果

- 静默半开连接在约 30 秒内被发现，设备列表不再长期显示“已连接”。
- 空闲连接约每 10 秒产生一帧 `PING`，流量可以忽略。
- 连接死亡与信任状态解耦：心跳只关闭连接，不改变“是否信任”。
- 两端需要同时升级。旧版本不会响应 `PING`，会看到连接被关闭后重连的抖动；项目仍为预发布阶段，接受并记录该限制。

## 风险

- 读线程在发送 `PING` 时可能因对端不读而短暂阻塞；对端不读本身已说明连接不可用。
- 心跳周期和最大丢失次数是固定常量，暂不提供 UI 配置。
- 如果 mDNS 仍能看到对端但 TCP 路径单向中断，心跳会在约 30 秒内关闭连接；这是期望行为，但会表现为短暂的“未连接”。

## 备选方案

- **TCP keepalive**：系统默认间隔过长，无法满足及时性，否决。
- **只依赖 mDNS 丢失**：mDNS 仍可见但 TCP 半开时无效；mDNS 抖动还会误杀正常连接，否决。
- **读超时直接断链**：会误杀正常空闲连接，否决。
- **在业务层实现心跳**：每个 handler 都要重复处理 `PING`/`PONG`，配对端点也会被卷入，否决。
