# 0021. 同步组 + 项级版本向量 + 变更通知驱动的“先收后推”

- 状态：已接受
- 日期：2026-11-01
- 修订：组与信任模型由 [ADR-0029](0029-group-id-namespace.md)、[ADR-0030](0030-pairwise-trust-and-presence.md) 修订；项级版本向量与传播模型继续有效。
- 修订：[ADR-0004](0004-bidirectional-sync-with-conflict-copies.md) 的并发判定与传播模型
- 修订：[ADR-0035](0035-multi-group-single-root.md) 的 run 作用域与组键（一组一根，组 ID 取代 root ID）

## 背景

需求方确认：三台以上设备要同步同一目录，且模型用**同步组 + 版本向量**，而非严格二元同步对。严格二元对在多设备下会产生多角冲突与重复传输；而版本向量只能表达因果，不能决定胜负，必须配合明确的传播规则。

## 决策

### 1. 同步组

- 创建第一个同步根时生成**组 ID**（8 位 Base32，人类可输入；见 ADR-0024），同步根归属于某个组。
- 组是一份成员表，不是中心服务：没有协调者进程，任何成员都可离线。
- 成员两两之间的同步需**双向同意**（ADR-0024）。

### 2. 项级版本向量

- 每个 Item 存 `{nodeId → counter}` 的版本向量；`counter` 是该节点对该项自增的**逻辑计数**，不是墙钟。
- 删除产生**带向量的墓碑**，墓碑不立即物理删除，按 GC 规则清理。
- 判定：
  - 向量可比（一方严格支配）→ 直接采用新的那一版。
  - 向量不可比（双方都改）→ **并发**，按 ADR-0004 生成冲突副本，绝不静默选边。

### 3. 变更通知驱动的传播（变更方主导）

1. 本地变更经防抖后，向组内**在线的、已双向同意的**成员发送 `NOTIFY`，携带 `runId`、变更摘要、向量快照。
2. 收到 `NOTIFY` 的成员对**该组**临时进入 `RECEIVE_ONLY`，从发起方拉取，完成后恢复 `BIDIRECTIONAL`。
3. 接收完成后立即检查本地向量是否领先于源，若有未推送变更则**立即反向推送**（同一 run 内完成，不留尾巴）。
4. 一次 run 的作用域是“某个同步根 × 某个组”，不是整个节点。

### 4. 并发通知的仲裁

- `NOTIFY` 携带**逻辑时间（Lamport 计数器）**与 `deviceId`，组内按 `(logicalTime, deviceId)` 排序，取最早者作为本轮源，其余排队等待本轮结束。
- 不使用墙钟排序：设备时钟不可信。
- 排队有上限（默认 3 个待处理 run），超出则合并为一次后续同步。

### 5. 离线处理

- `NOTIFY` 不持久化、不补发。离线成员重连后执行一次常规双向同步，由向量判定是否并发。
- 因而系统的最终一致不依赖通知，通知只是**降低延迟**的优化。

### 6. 成员变更

- 新成员加入后默认无共享，需双方分别同意。
- 成员被移除/撤销后，其向量分量保留在历史版本中但不再增长；只有“所有成员均已确认收到更高版本”且超过保留期，才能 GC 该分量。

## 后果

- 版本向量会让每个 Item 多出几十字节；成员 ≤10 时可接受，超过则需要 DVV 压缩（新 ADR）。
- “先只收、后反推”要求状态机可重入且幂等：中断后重跑不能产生重复版本或重复冲突副本。
- 通知丢失时会退化为“下次同步才一致”，必须在 UI 上区分“已通知”和“已同步”。
- 逻辑时间需要持久化的 Lamport 计数器，重启后不得回退。
- 与 ADR-0004 的冲突副本策略一致；`base hash` 字段废弃。

## 备选方案

- **严格二元同步对**：实现与推理最简单，但多设备时冲突与重复传输显著。
- **同步组 + 星型 hub**：连接数少，但 hub 掉线全组停摆，弱化去中心化。
- **版本向量 + LWW**：不会产生副本，但时钟回拨会丢更新。
- **CRDT 文件树**：理论优雅，但二进制内容无法合并，且工程量极大。
